# ml/ — кухня для похожести артистов

Здесь считается всё, что потом попадает в приложение двумя файлами: моделью и индексом.
**В работе приложения эта папка не участвует** — она нужна, только когда нужно пересобрать
модель или пересчитать базу артистов.

## Что тут происходит

```
download.sh        качает artists.zip с Google Drive (9.8 ГБ, с докачкой)
preprocess.py      mp3 -> моно WAV нужной частоты + manifest.csv
embed_mert.py      WAV -> эмбеддинги MERT, все 12 слоёв, с чекпоинтами
evaluate_mert.py   какой слой лучше различает артистов — по метрике
export_mert_onnx.py  модель -> ONNX, эмбеддинги -> artist_index.bin
cleanup.sh         убирает промежуточные данные (wav | mp3 | archive)

evaluate_online.py   база из сети (превью Deezer) против архива друга — см. ниже

reference_check.py   эталон для сверки с C# — тот же алгоритм на Python
check_quantization.py проверка, портит ли квантизация выдачу
csharp-check/        консольная утилита: гоняет боевой C#-код вне GUI
```

## Как пересобрать с нуля

```bash
python3.12 -m venv .venv && .venv/bin/pip install -r requirements.txt
brew install ffmpeg
./scripts/download.sh
bsdtar -xf data/raw/artists.zip -C data/raw    # НЕ unzip, см. ниже
.venv/bin/python scripts/preprocess.py --sample-rate 24000 --out data/audio24 --manifest data/manifest24.csv
.venv/bin/python scripts/embed_mert.py         # ~45 минут на M4
.venv/bin/python scripts/evaluate_mert.py
.venv/bin/python scripts/export_mert_onnx.py
```

Начинали с PANNs CNN14 (сеть, обученная на звуках вообще) — она давала top-5 64%.
MERT, обученная на музыке, дала 75% на той же метрике, поэтому PANNs-скрипты удалены,
чтобы не путались под ногами.

## Грабли, на которые уже наступили

- **Системный `unzip` вешается на этом архиве.** macOS поставляется с UnZip 6.00 от 2009 года,
  он не тянет zip64 больше 4 ГБ: полчаса работы, 15 секунд CPU, 468 файлов из 1689. Нужен `bsdtar`.
- **MERT не отдаёт слои через `output_hidden_states`** — её код писался под transformers 4.x и в
  5.x молча возвращает `None`. Слои снимаются forward-хуками. Слой возвращает голый тензор, а не
  кортеж: `out[0]` тихо оставит только первый элемент батча.
- **Брать последний слой нельзя.** Качество растёт до пятого слоя и падает после: слой 5 даёт
  top-5 75%, последний — 55%, то есть хуже, чем PANNs, с которой начинали.
- **Квантизацию не включать.** int8 ужимает 208 МБ до 52, но роняет top-5 с 56% до 42%.
  Поканальная и uint8 не помогают, fp16-конвертер ломает граф.
- **Мерить только leave-one-album-out.** Треки одного альбома сведены вместе, и обычная метрика
  завышает результат почти вдвое (51% против 29% top-1) — модель узнаёт мастеринг, а не артиста.

## База из сети против архива (26.09.2026)

Вопрос: можно ли не собирать архив руками, а слушать треки из сети. Замер: запросы — полные
треки друга, галерея — 30-секундные превью Deezer, посчитанные боевым C#-кодом.

```bash
dotnet run --project csharp-check -c Release -- online <модель.onnx> ../MessedUpSearchA/Assets/Models/artist_index.bin \
    data/online_deezer 10 scripts/deezer_aliases.tsv
.venv/bin/python scripts/evaluate_online.py
```

На Deezer нашлись 30 артистов из 32 (нет Prettyfun и preshboyswag), по 9.8 превью на артиста:

```
галерея                                top-1   top-5
друг, вся база (leave-one-album-out)   42.4%   74.3%
друг, по 10 треков на артиста          37.2%   70.7%
Deezer-превью, как есть                42.8%   75.4%
Deezer-превью, без той же песни        38.8%   73.5%
```

Превью не хуже архива. Оговорка: у превью нет пометки альбома, поэтому leave-one-album-out
к ним не применить — в галерее могут быть другие песни с того же альбома, что и запрос,
а это завышает цифру (см. грабли про мастеринг). Честное сравнение — третья и четвёртая строки
против второй, и там разрыв в пару процентов, не больше. MERT на превью — 1.1 с на трек.

## Бит -> артист: линейка на type beat'ах (27.09.2026)

Все цифры выше — «трек С ГОЛОСОМ -> артист». Продукт получает голый бит, поэтому линейка
другая: 248 type beat'ов с SoundCloud, подписанных артистами индекса друга
(`crawler typebeats` -> `prepare_typebeats.py` -> `embed_mert.py` -> `evaluate_beats.py`).

```
случайно: top-5 15.6%
слой 5, top-3, без поправки (как было в приложении)   top-1 11.3%  top-5 40.7%
лучшие слои (2, 3, 5)                                 top-5 40.7–42.7% — в пределах разброса ±5 п.п.
слой 5, top-3, поправка на хабы                       top-1 12.9%  top-5 41.5%
```

- **Слой менять не нужно:** все 12 слоёв в пределах шума, пересборка ONNX и индексов не требуется.
- **Агрегация** (top-1/3/5, среднее, центроид) — тоже в пределах шума.
- **Хабы — главное.** Без поправки Yeat (153 трека в базе — три похожих найдутся всегда) стоит в
  топ-5 у 66% ВСЕХ битов. Поправка (минус средняя оценка артиста по фоновым битам) держит
  точность и опускает самого частого до 32%. Фон — `Assets/Models/background_beats.bin`
  (`export_background.py`), поправка — `HubCorrection` в приложении.
- Честный итог: подбор по звуку бьёт случайный в ~2.6 раза, но далёк от «75%». Дальше —
  шаги 2–3 плана качества (отделение вокала, обучаемая голова) и сравнение с CLAP.

## Инструменталы вместо треков с голосом (27.09.2026)

База из превью Deezer тех же 30 артистов, вокал отделён Demucs (`prepare_vocal_test.py`,
`evaluate_vocal.py`), запросы — те же 248 type beat'ов:

```
база                    top-5    самый частый в топ-5
треки с голосом         33.3%    44.6%
только инструментал     42.1%    31.2%
среднее двух            40.4%    40.0%
```

Инструментал лучше на +8.8 п.п. (парный бутстреп, 90% ДИ [+3.3; +14.2], 99% выборок в плюс).
Поэтому оба индекса v2 собираются по инструменталам:
- `references_v2.bin` («звучит как») — `export_references.py` из разделённых превью, центр — их среднее;
- `artists_index_v2.bin` — краулер: `listen --slices-only` (C#) ‖ `separate_embed.py` (Python: центральные 30 с,
  Demucs, MERT слой 5; вектор с голосом — для фильтра «рэпер или нет», инструментал — для поиска).
- Сверка: вектор Python-конвейера и C#-приложения на одном файле — косинус 0.9996.
- Скорость: 12 с на кусок при 60 с звука; обрезка до центральных 30 с -> 5 с. Большой прогон
  (~2000 артистов, ~8000 кусков) — `scripts/night_run.sh`, ориентировочно ночь плюс утро.

## Первый большой прогон (27–28.09.2026)

`scripts/night_run.sh 2000`: поиск закончился на 1011 рэперах — 16 жанровых запросов исчерпаны раньше
цели 2000 (для большего индекса нужны ещё запросы). Прослушивание 4.3 ч (C#: 2958 кусков, 10/мин),
разделение 5.3 с на кусок. После фильтров (названия + классификатор голоса) и минимума в 2 куска —
**652 артиста, `data/artists_index_v2.bin` 3.8 МБ**.

- Хабов в большом индексе почти нет: самый частый артист — в топ-10 у 18% type beat'ов.
- Шкала процентов перекалибрована под этот индекс (`HubCorrection`: 0.10 -> 0%, 0.50 -> 100%).
- Грабли: `query` учитывал артистов с одним куском, а экспорт — нет; один случайный трек давал
  завышенное сходство (6 из топ-9). Теперь минимум 2 куска и там и там.

## Обучаемая голова — не взлетела (28.09.2026)

`scripts/train_head.py`: линейная проекция поверх MERT, InfoNCE «type beat -> треки артиста».
Линейка выросла до 869 type beat'ов 30 артистов (`crawler typebeats --per-artist 30`). Проверка
по группам артистов: учим на 24, меряем на 6 незнакомых (галерея — все 30), фон хабов — только
обучающие биты.

```
вариант                 top-5    против «как сейчас», 90% ДИ
без головы (как сейчас) 41.9%
d=64                    44.5%    +2.6  [-0.2; +5.4]
d=128                   43.0%    +1.1  [-1.8; +4.0]
d=256                   44.0%    +2.1  [-0.7; +4.7]
d=768 от единичной      43.2%    +1.3  [-0.5; +3.0]
```

Критерий «ДИ целиком выше нуля» не пройден ни одним вариантом — голову не включаем. Вывод:
линейно из сырого MERT почти нечего выжать; дальше — темп, затем другая модель или дообучение.

## Темп (BPM) — поверх звука не помогает (28.09.2026)

`scripts/bpm_eval.py`. Детектор — librosa PLP с шагом 256: на 26 битах с темпом в названии 77% точно
(`beat_track` — 46%, чаще сбивается на 2/3 темпа). Темп сравнивается со сворачиванием октав (70 = 140).
Темп артиста — по превью Deezer. Параметры подбираются на 4 группах артистов, проверка на 5-й.

```
вариант                 top-5    против «как сейчас», 90% ДИ
как сейчас (MERT+хабы)  41.9%
мягкий штраф по темпу   42.1%    +0.2  [-0.9; +1.4]
жёсткий отсев           35.4%    -6.5  [-9.4; -3.6]
только темп, без звука  22.4%    (случайно 16.7%)
```

Темп внутри артиста гуляет почти как между случайными битами (0.17 против 0.23 октавы), а битмейкер
ставит на «X type beat» любой темп. В ранжирование не идёт; автоопределение темпа как поле бита — отдельно.

## Вся галерея: 30 ориентиров + 652 андеграунда (28.09.2026)

`scripts/evaluate_all.py`: те же 869 type beat'ов, но нужного артиста ищем среди 682, а не 30.

```
среди 30 (контроль)   top-5 41.9%
среди 682             top-1 0.2%  top-5 1.5%  top-10 3.3%  top-50 20.9%   (случайно top-5 0.73%)
медианное место нужного артиста: 160 из 682; андеграунда в топ-10 бита — 9.6 из 10
с z-нормировкой хабов top-5 3.9%, медиана 133
```

Это главный честный результат v0.7: вектор MERT отличает артистов внутри 30 крупных, но «X type beat»
ближе к ~150 случайным андеграунд-рэперам, чем к самому X. Средние векторы групп (биты / Deezer /
SoundCloud) не разъехались, так что простого «разного источника» не видно — проверить опытом:
прогнать 30 ориентиров через тот же краулер (SoundCloud, те же куски) и повторить.

**Опыт с источником** (`crawler seed-refs --db data/crawl_refs.db` -> тот же конвейер, 208 кусков).
У 5 ориентиров данных нет (404 на потоке у лейбловых треков, чужой профиль Autumn!, пустой Ecco2k) —
оба варианта меряны на одних 720 битах 25 артистов:

```
ориентиры из            среди 30   среди 682: top-5  top-10  медиана места
превью Deezer           41.2%                 1.5%   3.2%    156
SoundCloud, тот же конвейер 45.1%             4.6%   8.9%    140
```

Источник влияет (top-5 среди 682 втрое выше), но и с одним источником нужный артист в среднем на
140-м месте. Узкое место — сама модель: дальше другая модель или дообучение.

## Данные

`data/` целиком в `.gitignore`: там рипы коммерческих релизов. Ни аудио, ни что-либо, из чего его
можно восстановить, в репозиторий не попадает.

`artist_index.bin` (5.2 МБ) при этом лежит в репозитории и едет с приложением: это 1685 векторов
по 768 чисел, необратимая статистика звучания — восстановить из неё запись нельзя. Модель (208 МБ)
в репозиторий не влезает по лимиту GitHub и едет отдельным файлом в релиз.
